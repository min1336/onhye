**온혜 AI 남용·프롬프트 공격 방어 심층 조사**

조사일: 2026-10-28. 범위: 현재 코드의 사용자 상황 분류, 검색·추천 API, 공개 배포 전 필요한 비용·보안 통제. 공식 가이드·제공사 문서·원저 논문을 대조했다. 아래 정책 수치는 온혜 시제품을 위한 제안이며, 업계 표준이나 검증된 최적값이 아니다. 이번 작업은 조사이며 제품 코드·계정·결제 설정은 변경하지 않았다.

**결론**

온혜는 AI를 자유 대화나 실행 에이전트로 확대하기보다, 제한된 관심 분야 분류기로 유지하는 편이 현재 목적에 맞는다. 우선순위는 공격 문구를 더 많이 금지하는 것이 아니라, 서버가 유료 호출을 허용할 수 있는 조건과 자원 한도를 강제하는 것이다. 필터가 놓치거나 분류가 잘못돼도 비밀 접근·자동 신청·무제한 비용으로 이어지지 않도록 설계한다. 프롬프트 내 지시와 데이터 구분은 도움이 되지만 보안 경계 자체가 아니다. [NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection), [OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

**3. 공개 배포 전 최우선 방어 — 온혜 맞춤 제안**

**P0-A. AI 경로와 무료 탐색 경로의 한도를 분리한다.**

/api/analyze의 Gemini 요청에만 더 엄격한 사용자/세션 한도와 동시 호출 제한을 적용한다. /api/recommend와 GET 검색은 CPU·트래픽 기준으로 별도 제한한다. 단순 페이지 넘김이 AI 사용량을 소진하거나, AI 차단 때문에 무료 검색까지 멈추지 않게 한다. GET 검색에도 부하 방어가 필요하다. 분당 요청 수만 제한하면 허용된 요청이 동시에 몰리는 문제는 남는다.

시제품 시작값 제안: 서명된 익명 세션당 AI 분당 3회·하루 10회·동시 1회, 앱 전체 AI 동시 3회·하루 100회. IP 한도는 보조 신호로 두고 공용망 사용자를 모두 같은 사람으로 취급하지 않는다. 이 수치는 제한적인 시연용 출발점이며 실제 사용량·오차단·지연을 측정해 조정한다. 익명 세션은 다시 만들 수 있으므로 사람당 한도를 보장하지 못한다. 전체 호출 한도는 반드시 별도로 둔다.

다중 서버에서는 공유 저장소의 원자적 갱신으로 검사와 차감을 함께 처리해야 한다. 단순 조회 후 차감은 동시 요청에 의해 초과될 수 있다. 단일 서버도 재시작으로 한도가 초기화되지 않는 저장 방식이 필요하다. Redis의 Lua 등은 공유 카운터의 원자적 처리에 사용할 수 있다. [Redis 공식 가이드](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)

**P0-B. 유료 호출 직전에 전체 예산과 동시 호출 슬롯을 확보한다.**

앱 전체의 일일 호출 상한, 시간대별 급증 제한, 운영자 AI 중지 스위치를 둔다. 여러 인스턴스에서도 동일하게 적용한다. 저장소 장애로 한도를 판단할 수 없으면 Gemini 호출을 중단하고 직접 분야 선택·체험 모드로 안내한다. 타임아웃이나 연결 종료가 발생했다고 제공사 비용이 0이라고 간주해 한도를 무조건 환급하지 않는다. 재시도는 중복 과금 위험과 함께 설계한다.

동일 요청의 동시 중복은 세션·요청 ID·본문의 서버 HMAC을 묶어 처리한다. 같은 ID에 다른 본문을 보내는 요청은 거절하고, 중복 요청이 추가 모델 호출을 만들지 않게 한다. 완료 응답을 저장해 재사용하려면 별도의 보존·동의 정책이 필요하다. 분류 결과나 근거 문장도 민감정보를 포함할 수 있다. 현재의 “상담 내용 서버 미저장” 약속을 캐시 때문에 조용히 바꾸지 않는다. 단순 해시를 개인정보 익명화라고 간주하지 않는다.

위 구조는 본 조사의 설계 제안이다. 자원·비용 제한의 필요성은 [OWASP LLM10](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/)에 근거하며, 제시한 구체적인 수치·저장 방식은 표준의 의무값이 아니다.

**P0-C. 클라우드 예산 알림과 Spend cap을 구분한다.**

최신 Google 문서에는 Vertex AI 계열의 aiplatform.googleapis.com이 Spend cap 지원 서비스로 명시되어 있다. 일반 alerts-only 예산은 사용을 멈추지 않지만, Spend cap 예산은 지정 프로젝트·서비스의 새 사용을 차단할 수 있다. 월 단위이고 한 프로젝트·한 서비스 범위다. 집행에는 지연이 있으며 진행 중 요청과 지연에 따른 초과 비용은 청구될 수 있다. 따라서 정확한 금액 상한을 즉시 보장하는 장치로 설명하면 안 된다. 같은 프로젝트에서 해당 서비스를 사용하는 다른 앱에도 영향이 있을 수 있다. 온혜 계정에서 실제 설정 가능 여부와 현재 설정은 별도로 확인해야 한다. [Google Spend cap](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps), [일반 예산 알림](https://docs.cloud.google.com/billing/docs/how-to/budgets)

권장 조합은 앱의 선제 호출 제한 + Cloud Billing Spend cap + 이상 사용 알림이다. 클라우드 알림을 받은 뒤 결제 계정 전체를 끊는 방식을 첫 방어로 삼지 않는다. 검색 서비스와 AI 기능의 중지 범위를 분리한다.

**P0-D. 공개 AI 호출에는 서버 검증 가능한 봇 방어를 둔다.**

Turnstile 등을 사용한다면 브라우저 위젯 통과만 믿지 않고 백엔드에서 Siteverify를 호출한다. 성공 여부뿐 아니라 hostname과 action을 확인한다. 토큰은 5분 유효·일회성이므로 재사용·다른 동작용 토큰을 시험해야 한다. 검증 API 자체에도 호출 한도·타임아웃이 필요하다. 이상이 없던 일반 열람에 매번 검증을 강제하기보다 AI 분석 진입과 의심 패턴에 집중한다. 검증 실패·장애 시 AI는 호출하지 않고 수동 탐색을 제공한다. CAPTCHA는 정상 사용자 식별의 완전한 보장이 아니므로 예산 제한을 대체하지 않는다. [Cloudflare 서버 검증](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)

Origin 검사는 보조 웹 방어다. 인증·할당량·봇 검증은 별도다. 쿠키 세션을 도입하면 Secure·HttpOnly·SameSite 및 CSRF 방어도 설계한다. 허용 Origin은 요청자가 보낸 Host를 기준으로 새로 만들어 믿기보다 배포 환경의 고정 허용 목록으로 검증한다. 프록시 뒤에서 실제 IP를 해석할 때는 신뢰하는 프록시가 설정한 값만 사용한다. [OWASP REST 보안](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)

**4. 프롬프트 공격과 잘못된 분류의 영향 제한**

모델이 할 수 있는 일은 고정 분야 enum 선택으로 제한한다. API 키·접근 토큰·다른 사용자의 상담·관리자 설정은 모델 입력에 넣지 않는다. 모델이 반환한 URL을 방문하거나 SQL·셸·신청 API를 실행하는 경로를 만들지 않는다. 향후 외부 행동이 필요해지면 모델의 판단과 별개로 서버에서 권한·대상·매개변수를 검증해야 한다. 이 구조적 분리는 필터 정확도에만 기대는 것보다 중요하다. [NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection), [CaMeL 논문](https://arxiv.org/abs/2503.18813)

현재 스키마·원문 근거 검증은 유지한다. 다만 유효한 JSON과 입력에 존재하는 인용문만으로 의미의 정확성을 증명하지는 못한다. 사용자가 분야를 확인·수정할 수 있는 단계를 유지하고, AI 결과로 소득·장애·수급 자격을 확정하지 않는다. Google도 구조화 출력의 값과 의미를 애플리케이션에서 검증하도록 안내한다. [Google 구조화 출력](https://ai.google.dev/gemini-api/docs/structured-output)

현재 정부 공고·첨부 본문은 이 분류 모델에 입력되지 않는다. 향후 공고 RAG나 PDF 분석을 도입하면 외부 자료도 신뢰할 수 없는 데이터로 취급해야 한다. 공식 사이트에서 받았다고 그 안의 지시를 실행 권한으로 승격하지 않는다. [OWASP 간접 프롬프트 공격](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

**5. Model Armor 도입 판단**

| 항목 | 확인한 사실 | 온혜 적용 판단 |
| --- | --- | --- |
| 기능·가격 | 제품 페이지 기준 월 200만 토큰 무료, 초과분 100만 토큰당 USD 0.10 | 검토할 만한 보조 방어. Gemini 추론 비용과는 별도이며 제공 범위·계정 조건 재확인 |
| 한국어 | 공식 문서가 한국어를 필터 테스트 언어로 명시 | 한국어·띄어쓰기·짧은 표현·정상 민감 요청으로 실제 평가 필요 |
| 기본 동작 | 프로젝트 통합 설정 예시는 기본 검사 전용 모드. 차단 모드는 별도 설정 | “연결했다”와 “차단한다”를 구분해 확인 |
| 장애 동작 | Vertex 통합은 일부 미지원 지역·접속 장애·내부 오류에서 검사 없이 계속 처리할 수 있음 | 내장 통합을 무조건 실패 시 차단되는 보안 경계로 가정하지 않음 |
| 짧은 입력 | 프롬프트 공격 검사에서 3단어 미만은 NO_MATCH_FOUND 반환이라는 제한이 있음 | 해당 판정을 전체 안전성의 증명으로 사용하지 않음 |
| 지역·데이터 | 통합에는 지역·템플릿·문서 처리 제약이 있고 민감정보 마스킹 전달에도 제약이 있음 | 현재 global 호출 경로에서 실제 적용 여부·지역·로그 동작을 검증한 뒤 채택 |

근거: [가격](https://cloud.google.com/security/products/model-armor), [개요·언어·짧은 입력 제한](https://docs.cloud.google.com/model-armor/overview), [Vertex 통합 제한과 모드](https://docs.cloud.google.com/model-armor/model-armor-vertex-integration), [다국어·지역별 검사](https://docs.cloud.google.com/model-armor/sanitize-prompts-responses)

도입 시 “공격 탐지”와 “유해 콘텐츠 탐지”를 구분한다. 가정폭력·성폭력·건강 문제에 대한 지원 요청을 유해 주제라는 이유만으로 차단하지 않도록 검증한다. 수동 REST 검사로 실패 시 차단 정책을 직접 구현하는 대안도 있으나, 검사 실패 시 Gemini가 호출되지 않는 순서를 앱에서 보장해야 한다. 보안 검사 서비스의 비용·지연·할당량도 보호 대상이다. 프로젝트 설정은 이번 조사에서 활성화하지 않았다.

**6. 공개 웹 서비스·개인정보 운영**

유료 호출 전용 서비스 계정에 필요한 권한만 부여한다. 로컬 ADC를 쓴다는 사실만으로 배포 권한이 최소라는 결론은 낼 수 없다. 실제 계정과 IAM 바인딩을 따로 확인한다. 런타임 계정에 예산 해제·IAM 변경 같은 관리자 권한을 주지 않는다. [Cloud Run 서비스 신원](https://docs.cloud.google.com/run/docs/securing/service-identity)

외곽 WAF·레이트 리밋은 큰 트래픽을 줄이는 보조 수단이다. Cloud Armor 공식 문서는 한도가 근사적이며 지역별로 적용될 수 있으므로 엄격한 쿼터 용도로 사용하지 말라고 설명한다. 비용 상한은 앱에서 따로 처리한다. Cloud Run 뒤에 붙일 경우 기본 URL로 우회하지 못하게 ingress도 설정해야 한다. 아직 배포 환경이 정해지지 않았으므로 유료 WAF를 필수 구매 대상으로 정하지 않는다. [Cloud Armor 한도 특성](https://docs.cloud.google.com/armor/docs/rate-limiting-overview), [Cloud Run ingress](https://docs.cloud.google.com/run/docs/securing/ingress)

보안 로그에는 시간, 요청 ID, 가명화된 세션 식별자, 라우트, 허용·거절 이유 코드, 지연, 모델 버전, 입력·출력 토큰 수 정도를 남기는 설계를 권한다. 상담 원문·AI 근거 문장·접근 토큰·주민번호·질병·가구 재산을 기본 로그에 남기지 않는다. 프록시·호스팅·보안 검사 제품의 로그도 별도로 확인한다. 보존 기간·열람 권한·삭제 정책은 배포 전 확정하고 개인정보 안내에 반영한다. 현재 서버 미저장 약속과 충돌하는 장기 상담 캐시는 보류한다. [OWASP 로그 제외 항목](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

**7. 검증 계획 — 아직 실행하지 않은 추가 시험**

기존 테스트는 스키마·근거·동의·오류 처리를 검사하지만 실제 모델을 상대로 한 보안 성능 보장은 아니다. 아래 시험은 추가 구현 이후의 합격 기준 제안이며, 이번 조사에서 유료 모델 공격 실험은 실행하지 않았다.

| 시험 | 확인할 결과 |
| --- | --- |
| 인사만 입력 / 인사+복지 요청 | 인사만은 AI 0회, 정상 복지 요청은 실수로 무시하지 않음 |
| 정상적인 피해 지원·질병·임신 관련 입력 | 정상 과업 완수와 보안 오차단을 별도 기록 |
| 역할 변경 지시 / 정상 상황과 공격 지시 혼합 | 분야 정확성, 스키마 준수, 권한 경계 각각 평가 |
| 한·영 혼합·띄어쓰기 변형·인코딩·보이지 않는 문자 | 정규식과 탐지기 우회 여부 및 정상 다국어 오차단 측정 |
| 유효하지만 틀린 분야와 실제 입력 인용문 | 문자열 근거 통과를 의미 정확성으로 오인하지 않음 |
| 브라우저 우회 직접 API 요청 | 동의 플래그·Origin만으로 무제한 유료 호출되지 않음 |
| 위조·만료·재사용·다른 hostname/action 봇 토큰 | 검증 실패 시 Gemini 호출 0회 |
| 같은 요청 ID 동시 중복 / 다른 본문 재사용 | 중복 모델 호출 방지, 본문 불일치 거절 |
| 한도 마지막 1회에서 동시 요청 | 여러 인스턴스에서도 승인 호출 수가 남은 한도 이하 |
| 세션 재발급·IP 변경·프록시 헤더 조작 | 개인 한도 우회가 전체 유료 한도 우회로 이어지지 않음 |
| 저장소·보안 검사·제공사 타임아웃 | 정한 실패 정책 준수, 무한 재시도·자동 비용 환급 없음 |
| AI 전체 중지 / 예산 소진 | Gemini 호출 0회, 검색·직접 분야 선택은 계속 동작 |
| 페이지 이동·필터 변경·담기 | Gemini 호출 0회 유지 |
| GET 검색 대량 요청 | AI 비용과 별개로 서버 CPU·트래픽 보호 |
| 로그 검사 | 입력 원문·토큰·개인 식별정보가 기록되지 않음 |

평가는 공격 성공률만 보지 않는다. 정상 과업 완수율·오차단율·호출 수·토큰 비용·지연을 함께 기록하고, 모델·프롬프트·정책 버전과 입력별 판정을 보존한다. 적응형 공격 연구는 고정된 공격 예시만 통과하는 방어를 경계하게 한다. AgentDojo는 도구 사용 에이전트용이므로 그 수치를 온혜 분류기의 방어율로 옮겨 쓰면 안 된다. CaMeL도 연구용 구현을 그대로 제품 보안 장치로 설치하는 추천은 아니다. [적응형 공격 연구](https://arxiv.org/abs/2503.00061), [AgentDojo](https://arxiv.org/abs/2406.13352), [CaMeL 연구 구현의 주의사항](https://github.com/google-research/camel-prompt-injection)

**8. 권장 작업 순서와 완료 기준**

| 우선순위 | 작업 | 완료 기준 |
| --- | --- | --- |
| P0 | AI 전용 한도·전체 호출 예산·동시성·중복 방지 | 호출 승인 전에 원자적 검사, 초과·중복·장애에서 모델 호출 없음 |
| P0 | 인사·사용법 로컬 응답과 수동 탐색 대안 | 불필요한 모델 호출 감소, 모호한 정상 요청 보존 |
| P0 | 공개 AI API 진입의 서버 봇 검증·세션 정책 | UI 우회 요청도 같은 검증을 거침 |
| P0 | 제공사 Spend cap·최소 권한 계정·중지 스위치 확인 | 계정의 실제 설정 증거와 중지 범위 확인 |
| P1 | GET·추천의 별도 부하 제한과 개인정보 없는 운영 지표 | AI 제한과 열람 제한 분리, 로그 민감정보 검사 |
| P1 | 한국어 정상·공격 회귀 모음 및 동시성 시험 | 사례별 결과·실패·비용·오차단을 재현 가능하게 기록 |
| P2 | Model Armor 비교 평가 후 도입 여부 결정 | 적용 지역·모드·장애·짧은 입력·오차단·가격을 확인 |
| 향후 | 공고 RAG·첨부 분석·자동 신청 등 기능 확장 | 외부 데이터 신뢰 경계와 실행 권한을 별도로 재설계 |

이번 조사의 한계: 실제 클라우드 계정의 Spend cap·IAM·Model Armor 설정, 유료 실모델 공격 실험, 분산 부하 시험은 확인하지 않았다. 코드 근거는 조사일의 작업 폴더 기준이며 향후 변경되면 다시 확인해야 한다. 모든 공격을 막는다고 보장하는 설계는 아니며, 잘못된 분류와 남는 공격 가능성의 영향을 제한하는 설계다.
